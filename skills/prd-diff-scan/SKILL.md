# PRD / UI 原型差异扫描

## 概述

逐页面、逐要素对比 PRD、UI 原型 / 截图 与当前项目实现，产出页面级证据，而非模块级总结。

本 skill 通常由 `brainstorming` 在步骤 2 自动调用。也可以单独使用。

如果同时提供了 **PRD + UI 图 / 原型图 / 截图**，且这些图片在当前运行中**可访问**，必须按 **PRD ↔ UI 图 ↔ 当前实现** 三方对比输出。

如果所谓“原型图”只是 **外部 URL / 内网地址 / 鉴权链接 / 当前运行不可访问的图片引用**，则**不得把它继续当作页面级对比输入源**。此时只能输出：

- `PRD ↔ 当前实现` 对比
- `原型图证据状态 / 证据不足项`

也就是说：**不可访问的 URL 型原型图，只记录，不参与页面级对比表。**

## 结束边界

如果用户明确表达以下任一意图：

- 只做差异扫描 / 只生成 diff 文档
- 不要进入 brainstorming / plan / 编码
- 先出差异分析结果，后续再说

则本 skill 在**步骤 7 落盘后必须立即停止**，不得自动调用或跳转到 `brainstorming`。

此时只允许输出类似 checkpoint：

```
✅ 差异扫描完成，文档已保存到 `docs/plans/YYYY-MM-DD-<主题>-diff.md`。
如需继续设计，请明确要求进入 brainstorming。
```

只有以下情况才允许进入下一阶段：

1. 本 skill 是由 `brainstorming` 明确作为前置步骤调用；或
2. 用户在差异扫描完成后，明确要求继续进入设计/brainstorming；或
3. 用户明确说明这是**自动测试 / 非交互**场景，并且明确授权：若无 blocker，差异扫描落盘后自动继续进入 brainstorming / 详细设计，无需逐轮等待确认。

## 自动测试 / 非交互模式（窄例外）

只有同时满足以下条件，才能启用这个模式：

- 用户明确说这是自动测试、CI、批处理或非交互场景
- 用户明确说：没有 blocker 时，默认采用推荐方案
- 用户明确说：默认同意继续下一步、默认同意落盘

启用后：

- 步骤 7 落盘后，如果**没有未解决 blocker**，可以直接继续进入 brainstorming / 详细设计
- 如果还有 blocker、关键信息缺失、PRD 与现状冲突无法自动决策，必须停止并把问题写清楚
- 不能把“自动测试”理解成“可以忽略证据不足”

## 证据原则

- **先记录证据，再下结论**：每个结论都要能追溯到 PRD、UI 图或代码文件
- **图片只证明可视信息**：页面标题、区块、字段、按钮、文案、标签、空态、布局、显隐状态等
- **不要从图片脑补不可见逻辑**：接口、权限、数据流向、状态流转、默认值来源等，若无法证明，标记为 `待确认` / `Blocker`
- **PRD 与 UI 图冲突时必须升级为 Blocker**：不能擅自决定谁为准

## 原型图证据不足处理

如果 PRD 中包含以下任一情况：

- Markdown 图片引用或外部图片 URL
- 内网图片地址、鉴权下载地址、已失效链接
- 只提到“见原型图”但当前运行拿不到图片文件

则必须执行下面的证据不足处理：

1. **提取并记录所有图片引用**（URL、本地路径、图片标识）
2. 判断每张图片是：`可访问` / `不可访问` / `未提供本地文件`
3. 在 diff 文档中新增 **“原型图证据状态”** 段落
4. 任何依赖这些图片才能确认的页面、字段、按钮、布局、提示文案、交互，均标记为 `待补图` 或 `Blocker`
5. 明确声明本次结论属于以下哪一类：
   - `PRD ↔ 原型图 ↔ 当前实现` 三方对比（证据完整）
   - `PRD ↔ 当前实现` 对比 + `原型图证据不足`（证据不完整）

当结论属于 `PRD ↔ 当前实现` 对比 + `原型图证据不足` 时，还必须满足：

- 页面级 UI 可视要素对比、控件矩阵、字段对比、9 维度对比 **不得再单列 `UI原型/截图` 列**
- 页面级对比表统一使用 `PRD | 当前实现 | 结论 | 是否阻塞/是否已核对` 这类结构
- 原型相关信息只允许出现在 `原型图证据状态` 和 `未核对项/Blocker` 中

禁止写法：

- 图片打不开，但默认原型图和 PRD 一致
- 没拿到原型图，却声称三方对比已完成
- 用猜测补齐按钮文案、布局、提示语、空态设计

## 前置条件

用户必须提供以下至少一项：
- PRD 文档（本地文件路径）
- UI 原型图 / 截图
- 粘贴的需求描述
- 外置规范文档

如果用户没有提供，告知用户："请提供 PRD 或需求文档的路径"，然后等待。

## 步骤 1：读取需求文档

1. 用 Read 工具读取用户提供的 PRD / 需求文档
2. 如果提供了 UI 原型图 / 截图，先判断是否为**当前运行可访问的本地文件或可读取图片**；只有可访问时，才逐张查看并记录图片路径、页面名称和可视要素
3. 如果项目中存在 `spec/index.md`，也读取它
4. 记录所有读取的文件路径

输出：

```
## 需求输入
- PRD: [文件路径]
- UI原型/截图: [文件路径列表或"无"]
- 项目规范: [spec/index.md 或 "无"]
```

如果有 UI 图 / 截图，额外输出：

```
## UI 图片证据

| 图片 | 对应页面/流程 | 可视要素摘要 | 明确看不到/无法判断 |
|------|--------------|-------------|-------------------|
| [路径] | [页面名] | [标题、字段、按钮、表格、标签等] | [数据来源、权限、状态流转等] |
```

如果 PRD 中引用的图片无法访问，必须改为输出：

```
## 原型图证据状态

| 图片引用 | 对应页面/流程 | 访问状态 | 不足原因 | 影响维度 | 是否阻塞 |
|---------|--------------|---------|---------|---------|---------|
| [URL/路径] | [页面名] | 不可访问/未提供 | [内网、鉴权、链接失效、无本地文件] | [按钮文案、布局、空态、交互等] | 是/否 |
```

## 步骤 2：探索现有实现

用 Agent（Explore 类型）或 Glob/Grep/Read 探索项目，找出与需求相关的现有代码。

必须了解：
- 哪些页面 / 接口 / 表已存在
- 哪些完全不存在
- 技术栈

输出：

```
## 项目现状
- 技术栈: [如 Vue 3 + Spring Boot + MySQL]
- 已有实现: [列出文件路径]
- 未实现: [列出缺失部分]
```

## 冲突判定规则

以下情况必须标记为 Blocker：

- 原型新增了 PRD 中没有的交互 / 字段 / 数据来源
- PRD 定义了原型中未展示的行为
- PRD 和原型在字段含义、触发条件、数据流向上不一致
- UI 图中出现 PRD 未定义的页面元素、按钮、文案、状态标签或布局变化
- 图片无法证明的控件状态、数据来源、权限、状态流转、默认值 / 排序 / 回显来源被模型自行补全
- 外置 spec 与 PRD / 原型 / 现状有矛盾
- 任何页面维度未核对
- "差异决议"只能记录用户已确认的结论，不可自行拍板

- 部分前端页面已存在

- 没有 UI 图可视要素对比证据
- 没有 9 维度交互/联动对比
- 没有页面级验收点
- 没有标注未核对维度
