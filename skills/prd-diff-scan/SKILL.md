# PRD 差异扫描

## 概述

逐页面、逐要素对比 PRD 与当前项目实现，产出页面级证据，而非模块级总结。

本 skill 通常由 `brainstorming` 在步骤 2 自动调用。也可以单独使用。

对比方式统一为 **PRD ↔ 当前实现** 双方对比。

---

## 快速决策：本次扫描模式（步骤 1 前必读）

按顺序回答，第一个"否"决定模式，之后不再往下判断：

```
Q1: 同任务目录下存在旧版本 diff 文档（`<旧commitid>/diff_<旧commitid>.md` 或兼容场景下的 `diff_*.md`）？
  否 → 全量扫描（读取全部原型文件）
  是 ↓
Q2: 旧 diff 文档中记录了完整 Git 基线（有 Commit ID + Commit 时间）？
  否 → 全量扫描
  是 ↓
Q3: git -C <原型目录> log -1 --format="%H" 的输出 == 旧 diff 的「当前原型 Commit ID」？
  是 → 直接复用（输出 checkpoint 后进入步骤 7 落盘，不重新扫描）
  否 ↓
Q4: 旧 diff 的 Commit ID 是当前 HEAD 的祖先（git merge-base --is-ancestor <旧SHA> HEAD）？
  是 → 增量刷新（只扫描 git diff 命中的文件）
  否 → 全量扫描
```

补充规则：
- 差异文档文件名固定为 `diff_<40位commitSHA>.md`，其中 commitSHA 必须是**当前原型仓库 HEAD**
- 只认版本化 diff 文件；旧 `diff.md` 一律视为**无合法基线**
- 同一任务目录下保留历史 diff 文件，不覆盖、不删除旧的 `diff_*.md`
- 如果 `当前原型 Commit ID != 无`，则当前版本产物必须落到 commit 命名的版本目录：`docs/plans/YYYY-MM-DD-<主题>/<当前commitid>/`
- 该 commit 版本目录中的 diff 路径固定为：`docs/plans/YYYY-MM-DD-<主题>/<当前commitid>/diff_<当前commitid>.md`

**确定模式后，在步骤 1 输出中明确写出选择了哪个模式及判断依据。**

**性能提示**：当 Q1=是、Q2=是时，将 Q3 + Q4 合并为单条 bash 一次执行，避免多次 Git 往返：

```bash
OLD_SHA="<旧Commit>"; HEAD_SHA=$(git -C <原型目录> log -1 --format="%H"); \
if [ "$OLD_SHA" = "$HEAD_SHA" ]; then echo "REUSE"; \
elif git -C <原型目录> merge-base --is-ancestor "$OLD_SHA" "$HEAD_SHA" 2>/dev/null; then echo "INCREMENTAL"; \
else echo "FULL"; fi
```

## 结束边界

如果用户明确表达以下任一意图：

- 只做差异扫描 / 只生成 diff 文档
- 不要进入 brainstorming / plan / 编码
- 先出差异分析结果，后续再说

则本 skill 在**步骤 7 落盘后必须立即停止**，不得自动调用或跳转到 `brainstorming`。

此时只允许输出类似 checkpoint：

```
✅ 差异扫描完成，文档已保存到 `docs/plans/YYYY-MM-DD-<主题>/<当前原型CommitID>/diff_<当前原型CommitID>.md`。
如需继续设计，请明确要求进入 brainstorming。
```

只有以下情况才允许进入下一阶段：

1. 本 skill 是由 `brainstorming` 明确作为前置步骤调用；或
2. 用户在差异扫描完成后，明确要求继续进入设计/brainstorming

## 证据原则

- **先记录证据，再下结论**：每个结论都要能追溯到 PRD 或代码文件
- **PRD 中无法明确的逻辑**：接口、权限、数据流向、状态流转、默认值来源等，若无法从 PRD 文字中确认，标记为 `待确认` / `Blocker`
- **不得脑补业务规则**：PRD 没写的，不能自行补全

## Git 基线获取

当用户提供了 UI / 原型 / 实现目录时，在开始读取源码前获取 Git 基线信息：

- 用单条 bash 一次获取仓库根目录 + commit ID + 时间：
  ```bash
  git -C <原型目录> rev-parse --show-toplevel && git -C <原型目录> log -1 --format="%H%n%cI"
  ```
- 若失败或不在 Git 仓库中 → 记录为 `无`，回退到全量扫描

获取基线后，按"快速决策"中的 Q1-Q4 判定本次扫描模式。

### 增量刷新规则

- 只允许把 `git diff --name-only <旧Commit>..HEAD -- <原型目录>` 命中的原型文件作为**重新核对范围**
- 只重新读取这些变更原型文件，并将它们映射到受影响页面 / 弹窗 / 抽屉 / 流程
- 未受影响的页面可沿用旧 diff 中的已核对内容，不要对未变文件重新做全量扫描
- 最终仍然要生成一份**新的完整 diff 文档**：文件名必须为 `diff_<当前HEAD_SHA>.md`。如果有当前 commit，则保存到 `docs/plans/YYYY-MM-DD-<主题>/<当前HEAD_SHA>/`。未受影响页面**直接从旧 diff 文档中复制对应章节原文**（不重新生成），受影响页面重做步骤 4-6，并重新生成差异清单、Blockers、建议决议和落盘前自检
- 如果 HEAD 已变化，但原型目录下没有任何变更文件，也要生成新的 diff 文档，明确写出“自 `<旧Commit>` 以来原型目录无变更文件”，并把 `当前原型 Commit ID / 时间` 更新到最新值
- 如果旧 diff 中无法解析 commit id，或 `git merge-base --is-ancestor <旧Commit> HEAD` / `git diff` 失败，则回退到**全量扫描**

## 前置条件

用户必须提供以下至少一项：
- PRD 文档（本地文件路径）
- 粘贴的需求描述
- 外置规范文档

如果用户没有提供，告知用户："请提供 PRD 或需求文档的路径"，然后等待。

## Step 0：路径与基线歧义确认（开始流程前必做）

在执行任何 `Read`、`Glob`、`Grep`、Git 基线命令或源码扫描之前，先确认以下 3 个输入是否明确：

1. **实际修改的代码目录**：本次最终要落代码的目标项目目录
2. **UI 原型实现目录**：用于做 PRD ↔ 当前实现对比的原型 / UI / 当前实现目录
3. **上一次 diff 文件**：本次要复用或增量刷新的上一份版本化 diff 文档

如果这 3 项中任意一项出现以下情况，则视为**不明确**：

- 用户消息里没有明确给出路径
- 本地探索能找到多个合理候选（例如多个前端目录、多个原型目录、多个任务目录或多个历史 diff）
- 能找到候选，但无法安全判断哪个才是本次任务要用的目录 / diff
- 当前工作目录与用户给出的目录线索明显不一致

**不明确时的硬门禁**：

- **必须使用 `AskUserQuestion` 工具**向用户确认
- **不得自行猜测，不得直接继续步骤 1**
- **用户确认后**，才能继续后续 Git 基线获取和差异扫描流程

### AskUserQuestion 的提问要求

- 一次最多确认这 3 项：实际修改的代码目录 / UI 原型实现目录 / 上一次 diff 文件
- 问题中列出 2-4 个明确候选路径，并给出推荐项
- 如果某项没有任何可靠候选，也要明确写成 `无明确候选，需要用户提供路径`
- 等用户回答后，把最终确认结果写入步骤 1 的「比对基线」

### 原型目录与开发项目的区分

本 skill 涉及**两个不同的目录**：

1. **原型目录**（又称"当前实现目录"）：用户提供的 UI / 原型 / 实现目录（如 `ruoyi-ui/`），用于 PRD ↔ 当前实现的逐页对比（步骤 2-6）
2. **开发项目目录**：最终生成代码的目标项目，即**当前工作目录**（`cwd`），用于步骤 6.5 变更文件清单中判定"开发文件状态"和"合并策略"

原型目录和开发项目可能是同一个目录，也可能是完全不同的仓库。步骤 6.5 中"在开发项目中检查对应路径"的映射规则：

- 默认：**原型目录中的相对路径 = 开发项目中的相对路径**（如原型 `src/views/order/myOrder.vue` → 开发项目 `src/views/order/myOrder.vue`）
- 如果原型目录的项目结构与开发项目不同（如原型根目录是 `ruoyi-ui/` 但开发项目是 `frontend/`），在步骤 1 输出的比对基线中记录映射前缀：`开发项目路径前缀: [如 "frontend/" 或 "—"（相同结构）]`
- 如果用户明确指定了映射规则，按用户指定执行

## 步骤 1：读取需求文档

**以下两项并行执行**（在同一轮对话中同时发起）：
1. 用 Read 工具读取用户提供的 PRD / 需求文档
2. 用 Bash 执行 Git 基线获取命令（见"Git 基线获取"节）

**前提**：Step 0 中的「实际修改的代码目录」「UI 原型实现目录」「上一次 diff 文件」必须已经明确；若仍不明确，返回 Step 0 用 `AskUserQuestion` 向用户确认。

完成后记录所有读取的文件路径。

输出：

```
## 需求输入
- PRD: [文件路径]

## 比对基线
- 原型目录: [文件路径或 "无"]
- 开发项目目录: [当前工作目录的绝对路径]
- 开发项目路径前缀: [如 "frontend/" 或 "—"（与原型结构相同）]
- Git 仓库根目录: [路径或 "无"]
- 当前原型 Commit ID: [SHA 或 "无"]
- 当前原型 Commit 时间: [ISO 8601 或 "无"]
- 上次 diff 文档: [路径或 "无"]
- 上次 diff Commit ID: [SHA 或 "无"]
- 比对模式: [全量扫描 / 直接复用 / 增量刷新]
- 本次重检文件: [全部原型文件 / 文件列表 / 无变更]
```

## 步骤 2：探索现有实现

用 Agent（Explore 类型）或 Glob/Grep/Read 探索项目，找出与需求相关的现有代码。

如果当前模式是**增量刷新**，这里的源码探索范围默认只包含：

- `git diff --name-only <旧Commit>..HEAD -- <原型目录>` 命中的原型文件
- 这些文件直接对应的页面 / 弹窗 / 抽屉 / 跳转流程
- 为了更新差异清单 / Blockers / 建议决议而必须回读的旧 diff 内容

不要把未命中的原型文件重新纳入全量核对范围；未受影响页面应从旧 diff 继承。

必须了解：
- 哪些页面 / 接口 / 表已存在
- 哪些完全不存在
- 技术栈

**关键：必须用 Read 工具读取每个已存在页面文件的完整源码。** 仅确认文件存在而不读取内容是不够的——步骤 4 需要对比页面上的每个控件、字段、交互行为，不读源码就无法做真实对比。

如果页面文件较多，**必须并行读取**（在同一轮对话中发起多个 Read 工具调用，每批 5-8 个文件），不要逐个串行读取。**进入步骤 4 之前必须确保所有已存在的页面文件都已读取**。

输出：

```
## 项目现状
- 技术栈: [如 Vue 3 + Spring Boot + MySQL]
- 已有实现: [列出文件路径]
- 未实现: [列出缺失部分]
```

## 受影响页面清单

| 页面/流程 | 当前实现文件 | 核对状态 |
|-----------|-------------|---------|
| [页面名] | [文件路径或"不存在"] | 未核对 |
```

## 步骤 4：逐页面对比（核心）

对每个页面，依次检查以下内容。

**子页面/弹窗/抽屉也是页面。** 如果主页面包含内嵌弹窗、抽屉或子流程（如订单确认弹窗、发货弹窗），每个子页面也必须有完整的 5 维度对比表（UI 可视要素 + 控件矩阵 + 字段对比 + 9 维度 + 验收点），格式与主页面一致。不得因为是弹窗就简化为几行文字描述。

**禁止「待核对」作为对比结论。** 每个单元格必须填写明确结论：一致 / 差异 / 缺失 / 新增 / 部分差异。如果某页面文件存在但源码未读取，必须先回到步骤 2 读取，然后才能填写对比表。对比表中出现「待核对」「需核对」等未决结论 = 差异扫描未完成，不得落盘。

控件矩阵最少覆盖以下类别：筛选控件、表格列、按钮/菜单、状态标签、弹窗/抽屉入口、分页/工具栏、空态/提示文案。

### 4.4 交互 / 联动对比

每个页面按 **9 大维度** 逐项检查：

| 维度 | 检查内容 |
|------|---------|
| **交互行为** | 按钮、菜单、弹窗、跳转、返回路径、二次确认 |
| **触发事件** | 点击、切换、分页、搜索、自动刷新、定时触发 |
| **数据来源** | 接口、字典、枚举、配置、外部系统、静态常量 |
| **数据流向** | 展示字段来自哪里，提交后落到哪里 |
| **字段联动** | 显隐、禁用、必填切换、联动清空、级联请求、自动带出 |
| **状态流转** | 状态机、启停、草稿/发布、异常分支 |
| **权限与角色** | 谁可见、谁可操作、按钮/菜单/接口权限归属 |
| **默认值 / 排序 / 回显** | 默认选项、默认排序、默认分页、初始化条件、回显来源 |
| **下拉/字典来源** | 固定值、字典接口、级联依赖、label/value 结构 |

此外，每个页面必须补充一个**验收点**小节。`验收点` 不计入 9 大维度，但如果未核对，必须出现在"未核对项"里，并可直接判定为 `Blocker`。

```
### [页面名称] — 验收点

- 正向场景: [用 1-2 句话描述可验证的操作路径，如"选中 2 条待确认订单 → 点击订单确认 → 调用接口成功 → 状态变为已确认"]
- 空态: [列表无数据时的展示和可操作控件，如"表格显示暂无数据，查询/新增按钮仍可用"]
- 异常态: [接口失败/校验不通过时的行为，如"SAP 返回错误 → 弹窗提示 SAP 返回的信息，状态不变"]
- 权限态: [不同角色看到的差异，如"管理员看全部数据；供应商仅看所属订单，他人订单不可见"]
```

### 4.5 未核对项

## 未核对项
- 页面: [名称]
  - 未核对维度: [列表]
```

未核对维度自动视为 Blocker。

### 4.6 页面完成 Checkpoint

**每个页面的 4.1～4.5 全部完成后，必须输出以下 checkpoint 再继续下一页面：**

```
✓ [页面名称] UI要素:__ 控件:__ 字段区:__ 9维度:__ 本页D__/B__（差异__条/阻塞__条）
  累计: D__/B__（已完成 __/__ 页）
```

数字必须真实计数。输出此行之前如发现任何格未填或结论为「待核对」，必须先补全。

**累计计数规则**：每个 checkpoint 的累计行记录截至当前页面（含）的差异 / 阻塞总数。步骤 6 汇总时直接使用最后一个 checkpoint 的累计数作为基准，无需回看所有对比表重新计数。

## 步骤 6：汇总差异 + Blockers

```
## 差异清单

| 编号 | 差异描述 | 差异类型 | 影响范围 | 是否阻塞 |
|------|---------|---------|---------|---------|
| D1 | [描述] | [可视要素/字段/9维度之一] | 前端/后端/数据库 | 是/否 |

## Blockers（需用户确认）

1. **B1**: [问题] — 建议: [选项]
2. **B2**: [问题] — 建议: [选项]

## 建议决议（逐项待确认）

从 D1 到 D{最后编号} 和 B1 到 B{最后编号} **必须逐行不间断列出**，不得跳过任何编号：

| 编号 | 差异/问题摘要 | 建议处理方案 | 用户确认 |
|------|-------------|-------------|---------|
| D1 | [差异描述] | [保持现状 / 按 PRD 修改 / 其他] | ⏳ 待确认 |
| D2 | [差异描述] | [方案] | ⏳ 待确认 |
| ... | （从 D1 到 D{N} 每个都要列） | ... | ... |
| B1 | [Blocker 描述] | [方案 A / 方案 B] | ⏳ 待确认 |
| ... | （从 B1 到 B{M} 每个都要列） | ... | ... |

> **统计行（必填）**：本表共 __ 行 = D1-D{N} 共 __ 项 + B1-B{M} 共 __ 项

如果差异清单有 D1-D12 共 12 项、Blockers 有 B1-B6 共 6 项，则此表必须有 18 行，**缺一行即不合格**。

## 差异决议

用户逐项确认后，将上表「用户确认」列更新为 ✅ + 用户选择的方案。
全部确认后方可进入 brainstorming。
```

**差异类型** 从以下类型中选填：可视要素 / 控件 / 字段 / 交互行为 / 触发事件 / 数据来源 / 数据流向 / 字段联动 / 状态流转 / 权限与角色 / 默认值 / 排序 / 回显 / 下拉字典来源 / 验收点

### 差异清单完整性规则

差异清单必须**完整反映**步骤 4 和步骤 5 中发现的所有差异：

1. **逐行扫描**：步骤 4 每张对比表中，「结论」列为「差异」「缺失」「新增」「部分差异」的**每一行**，都必须在差异清单中有对应的 Dx 编号。**包括子页面/弹窗的对比表，也包括 9 维度表中的差异行**——不得因为"同类差异"或"影响较小"而跳过
2. **后端同步**：步骤 5 的接口/数据库对比表中，「是否一致」为「否」的每一行，也必须有对应 Dx
3. **禁止合并**：不同页面、不同维度的差异不能合并成一条笼统描述（如「前端部分实现」「后端未实现」不能代替逐项差异）
4. **Blocker 同步**：差异清单中「是否阻塞=是」的每一条，必须在 Blockers 列表中有对应 Bx
5. **建议决议覆盖**：建议决议表必须从 D1 到 D{最后编号}、B1 到 B{最后编号} 逐行列出，不得跳过任何编号
6. **追溯校验**：完成差异清单后，将 Dx 总数与最后一个页面 checkpoint 的累计差异数（+ 步骤 5 后端差异数）对比。若 Dx 总数 < 累计值，按各页面 checkpoint 的「本页 D」数定位遗漏页面，仅回看该页面的对比表补充 Dx

违反此规则 = 差异扫描不合格，必须补全后重新落盘。

## 步骤 6.5：变更文件清单

当比对模式为**增量刷新**或**全量扫描**时，必须在当前 diff 文档（`diff_<commitid>.md`）中输出一个文件级变更表格，供后续 writing-plans / executing-plans 使用。

### 获取变更文件

- **增量刷新**：`git -C <原型目录> diff --name-status <旧Commit>..HEAD -- <原型目录相对路径>` 获取变更文件及类型（A=新增 / M=修改 / D=删除）
- **全量扫描**：列出原型目录下所有**与 PRD 相关**的文件，变更类型统一标为 `全量`

#### 全量扫描时的"相关文件"定义

只列出与 PRD 涉及的业务页面/功能直接相关的文件，**不包含**框架基础设施、构建配置、通用组件等。具体范围：

| 类别 | 包含 | 排除 |
|------|------|------|
| 页面文件 | `src/views/` 下被 PRD 涉及的 `.vue` 文件 | 不在 PRD 范围内的页面 |
| API 文件 | `src/api/` 下被 PRD 涉及页面直接使用的 `.ts` 文件 | 通用 API（如 `login.ts`、`menu.ts`） |
| 类型定义 | `src/types/api/` 下与涉及页面 API 对应的 `.ts` 文件 | 通用类型（如 `common.ts`） |
| 路由配置 | `src/router/index.ts`（仅当 PRD 涉及路由变更时） | — |
| Mock 数据 | `mock/` 下与涉及页面相关的文件 | — |
| SQL 文件 | `docs/sql/` 或 `sql/` 下与涉及功能相关的文件 | — |
| 后端文件 | Controller / Service / Mapper / Entity / XML（如有） | 框架基础类 |

如果无法判断某文件是否相关，宁可多列也不要遗漏——由后续 writing-plans 决定是否纳入 Task。

### 判定开发文件状态

对变更文件**批量**检查开发项目中的对应路径（按步骤 1 记录的路径映射规则）：

**批量操作（减少 IO 往返）**：
- **存在性**：用 Glob 一次性匹配所有对应路径，而非逐个 Read 判断
- **摘要对比**：用单条 bash 批量计算校验和，避免逐文件 Read 全文：
  ```bash
  # 旧版本摘要
  for f in <文件列表>; do echo "$f $(git -C <原型目录> show <旧Commit>:"$f" 2>/dev/null | git hash-object --stdin)"; done
  # 开发文件摘要
  for f in <开发文件列表>; do echo "$f $(git hash-object "$f" 2>/dev/null || echo MISSING)"; done
  ```

判定规则：

1. 文件不存在（MISSING） → `不存在`
2. 文件存在且 hash 一致 → `已存在（与旧原型一致）`（开发者未做本地修改）
3. 文件存在且 hash 不一致 → `已存在（有本地改动）`（开发者做了本地修改）
4. 全量扫描模式下无旧版本可比 → 文件存在即标 `已存在（需人工判断）`

### 推断合并策略

| 变更类型 | 开发文件状态 | 合并策略 |
|---------|------------|---------|
| 新增 | 不存在 | 复制 + 适配 |
| 新增 | 已存在 | 智能合并 |
| 修改 | 不存在 | 复制 + 适配（需确认） |
| 修改 | 已存在（与旧原型一致） | 直接覆盖 |
| 修改 | 已存在（有本地改动） | 智能合并 |
| 删除 | 不存在 | 无操作 |
| 删除 | 已存在 | 待用户确认 |
| 全量 | 不存在 | 复制 + 适配 |
| 全量 | 已存在（需人工判断） | 智能合并 |

### 输出格式

```
## 变更文件清单

> 基线 Commit: `<旧SHA 或 "无">` → 当前 Commit: `<新SHA>`
> 变更文件数: N

| # | 原型文件（相对原型目录） | 变更类型 | 开发项目对应文件 | 开发文件状态 | 合并策略 | 备注 |
|---|------------------------|---------|----------------|------------|---------|------|
| F1 | [路径] | [新增/修改/删除/全量] | [路径或 "—"] | [状态] | [策略] | [如"未被路由使用，建议删除"或留空] |
```

```

| # | 检查项 | 实际结果（必须填数字） | 通过? |
|---|--------|----------------------|------|
| 1 | 页面完整性: PRD 涉及 __ 个页面，文档对比了 __ 个页面 | [填入两个数字] | ✅/❌ |
| 2 | 维度完整性: | [逐页列出] | ✅/❌ |
|   | - 页面1 [名称]: UI可视要素 ✅/❌, 控件矩阵 ✅/❌, 字段对比 ✅/❌, 9维度 ✅/❌, 验收点 ✅/❌ | | |
|   | - 页面2 [名称]: ... (每页一行) | | |

| 3 | 差异映射: 对比表中「差异/缺失/新增/部分差异」共 __ 行 → 差异清单共 __ 条 Dx | [填入两个数字，前者 ≤ 后者] | ✅/❌ |
| 4 | Blocker 同步: 差异清单中「是否阻塞=是」共 __ 条 → Blockers 共 __ 条 Bx | [填入两个数字，必须相等；禁止多条阻塞差异归纳成一条 Bx] | ✅/❌ |

```

**自检格式要求**：
- 每个 `__` 处必须替换为实际数字
- 检查项 2 必须逐页展开，不得写"所有页面已完成"
- 检查项 3 的左侧数字（对比表差异行总数）直接取最后一个页面 checkpoint 的累计差异数 + 步骤 5 后端差异数，无需回看每张表
- 检查项 4 要求**阻塞差异数 = Blocker 数**，禁止把多条阻塞差异归纳成一条笼统 Blocker（如"后端完全缺失"不能合并 D3-D8 六条接口 Mock 差异）
- 若原型目录位于 Git 仓库中，检查项 7 中的 `当前原型 Commit ID / 时间` 不得为空
- 任何一项为 ❌ 时必须补全，补全后重新自检

### 保存

保存内容中必须包含以下节；如果原型目录位于 Git 仓库中，这一节缺失 = diff 文档不合格：

```md
## 比对基线

- PRD: [路径]
- 原型目录: [路径]
- 开发项目目录: [当前工作目录的绝对路径]
- 开发项目路径前缀: [如 "frontend/" 或 "—"（与原型结构相同）]
- Git 仓库根目录: [路径或 "无"]
- 当前原型 Commit ID: [SHA 或 "无"]
- 当前原型 Commit 时间: [ISO 8601 或 "无"]
- 上次 diff 文档: [路径或 "无"]
- 上次 diff Commit ID: [SHA 或 "无"]
- 比对模式: [全量扫描 / 直接复用 / 增量刷新]
- 本次重检文件: [全部原型文件 / 文件列表 / 无变更]
```

把以上全部内容保存到当前版本目录中的 diff 文件：

- 有当前原型 Commit ID：`docs/plans/YYYY-MM-DD-<主题>/<当前原型CommitID>/diff_<当前原型CommitID>.md`
- 无当前原型 Commit ID：`docs/plans/YYYY-MM-DD-<主题>/diff_<当前原型CommitID>.md`

保存前需先创建任务目录 `docs/plans/YYYY-MM-DD-<主题>/`（如果不存在）。若存在当前 commit，还需创建版本目录 `docs/plans/YYYY-MM-DD-<主题>/<当前原型CommitID>/`。

如果当前 HEAD 对应的同名文件已存在且比对模式为 `直接复用`，则直接返回该文件路径，不新建文件。

差异扫描结果必须落盘，不能只存在于聊天记录中。

落盘后执行以下分支：

- **Standalone 模式**（用户只要差异扫描）：输出保存路径后 `STOP`，等待用户下一步指令
- **brainstorming 前置模式**：告知差异扫描已完成，可返回 `brainstorming` 继续后续设计

## 冲突判定规则

以下情况必须标记为 Blocker：

- PRD 定义了当前实现中未展示的行为
- PRD 和当前实现在字段含义、触发条件、数据流向上不一致
- PRD 中无法明确的控件状态、数据来源、权限、状态流转、默认值 / 排序 / 回显来源被模型自行补全
- 外置 spec 与 PRD / 现状有矛盾
- 任何页面维度未核对
- "差异决议"只能记录用户已确认的结论，不可自行拍板

## 反面示例

以下输出**不合格**：

- "前端部分实现，后端尚未实现" / "页面看起来基本一致" → 缺少页面级对比证据
- 建议决议只有 4 条笼统总结，但差异清单有 12 个 Dx → 每条差异必须有对应建议
- 页面 1 有完整对比，页面 2-4 缺控件矩阵/9 维度/验收点 → 每个页面必须完整
- 对比表中标注「差异」的行未出现在差异清单中 → 不得遗漏
- 落盘前自检只写"✅ 已完成"而没有实际数字 → 自检必须展示数量对比
- 页面文件存在但未 Read 源码，对比表填「待核对」→ 必须读取源码后才能写对比表
- 原型目录在 Git 仓库中但 diff 文档缺少 Commit ID/时间 → Git 基线缺失

---

## 完成条件

- 每个 PRD 涉及的页面都有控件矩阵 + 字段对比 + 9 维度对比 + 验收点（**4 项缺一不可**）
- 每个页面都有 UI 可视要素对比
- **文档中不存在任何「待核对」「需核对」结论**（出现即说明对比未完成，不得落盘）
- 所有差异已编号汇总
- **差异清单 Dx 数量 ≥ 所有对比表中「差异/缺失/新增」行的总数**（不得遗漏）
- **Blockers Bx 数量 = 差异清单中「是否阻塞=是」的行数**
- **建议决议表逐项覆盖所有 Dx 和 Bx**（不得用笼统总结替代）
- 未核对项已列出并标记为 Blocker
- Blockers 已列出
- 落盘前自检 8 项全部通过
- 若原型目录位于 Git 仓库中，文档已记录 `原型目录`、`Git 仓库根目录`、`当前原型 Commit ID`、`当前原型 Commit 时间`
- 结果已保存到当前版本目录中的 `diff_<当前原型CommitID>.md`

如果用户未要求继续，完成后必须停止并等待。
