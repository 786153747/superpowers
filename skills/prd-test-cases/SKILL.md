# PRD 场景测试用例生成

## Overview

从 PRD 和 `prd-diff-scan` 产出的 `diff.md` 中提取业务场景，生成步骤级测试用例，最终输出为 Excel(.xlsx) 文件。

每个测试用例按操作步骤拆解，每步有独立的预期结果，适合 QA 手工执行或导入测试管理工具。

**目标产物是“业务可执行的测试用例”，不是实现缺陷清单。**

以下内容默认不应写入 `test-cases.json` 或 Excel：

- `src/api/*.ts` 缺失
- import / 模块未找到 / 编译失败 / 构建失败
- `node_modules`、脚本依赖、控制台报错这类实现问题
- 后端未建表、接口未接入、Mock 未完成这类研发待实现项

这类问题应作为“待实现风险”或“交付前置条件”单独说明，不要伪装成 QA 手工回归用例。

## 前置条件

- PRD 文档（本地文件路径）
- `diff_<commitid>.md` 或 `diff.md`（`prd-diff-scan` 产物），提供页面清单、差异清单、验收点、控件矩阵
- 如果 diff 文档不存在，告知用户先执行 `prd-diff-scan`

## 输出产物

```
docs/plans/YYYY-MM-DD-<topic>/<commitid>/
  test-cases.json          # 中间 JSON（Claude 生成）
  test-cases.xlsx          # 最终 Excel（脚本生成）
```

上面的目录结构只是推荐示例，不要在未确认前直接假定为实际输出目录。

---

## Step 1: 确认输入

确认以下路径。只要用户没有明确给出输出目录，就必须先用 `AskUserQuestion` 确认；确认前不要继续执行生成步骤：

1. **PRD 文档路径**
2. **diff 文档路径**（`diff_<commitid>.md` 或 `diff.md`）
3. **输出目录**（可建议“与 diff 文档同目录”作为默认方案，但必须先得到用户确认）

并行读取 PRD 和 diff 文档。

输出：

```
## 输入确认
- PRD: [路径]
- diff 文档: [路径]
- 输出目录: [路径]
- 页面数量: [N]
```

---

## Step 2: 提取页面与场景

从 diff 文档中提取以下信息：

1. **受影响页面清单**（步骤 3 的页面表）
2. **每个页面的验收点**（步骤 4.4 的验收点小节）
3. **每个页面的控件矩阵**（步骤 4.2），包括按钮、表单、查询、弹窗等
4. **差异清单**（`Dx` 编号），用于关联测试用例
5. **Blockers / 待确认项**（`Bx` 编号，如存在）
6. **9 大维度对比**中标记为“差异”的项

从 PRD 中补充：

- 业务规则和约束
- 状态流转
- 权限角色定义
- 前后置条件
- 唯一性、幂等、重复提交、冲突规则
- 数据归属、可见范围、跨页面联动影响
- 导出命名、默认值、排序、固定列、分页等页面级细节

输出每个页面的场景大纲：

```
## 场景大纲

### [页面名称]（page-slug）
- 正向主流程: [场景列表]
- 反向校验 - 业务规则: [场景列表]
- 反向校验 - 状态流转: [场景列表]
- 反向校验 - 输入校验: [场景列表]
- 边界场景: [场景列表]
- 权限控制: [场景列表]
- 异常场景: [场景列表]
- 预计用例数: [N]
- 待实现风险（不进入测试用例）: [列表，可为空]
```

反向校验优先顺序：

1. 业务规则不满足
2. 状态流转不允许
3. 页面级输入校验

严格规则：

- 只把**业务可执行**的内容放进场景大纲。
- 只要是“页面标题缺失”“固定列不符”“高级搜索缺少字段”“按钮缺失”“弹窗流程不符”这类 UI/业务差异，后续必须落成明确断言。
- 只要是“接口未实现”“数据库未建表”“本地 API 文件缺失”“模块未找到”这类实现问题，后续不要生成成测试用例。
- 对于仅由通用组件或统一框架兜底、且没有业务差异的通用错误，不要为每个页面机械生成一条占位式反向用例。

**STOP，等用户确认场景大纲后再继续。**

## Step 3: 生成测试用例 JSON

按页面逐个生成步骤级测试用例，写入 `test-cases.json`。

### JSON 格式

```json
{
  "projectName": "项目名称",
  "generatedAt": "2026-03-19T10:00:00",
  "source": {
    "prd": "PRD 路径",
    "diff": "diff 文档路径"
  },
  "pages": [
    {
      "pageSlug": "my-order",
      "pageName": "我的订单",
      "testCases": [
        {
          "id": "TC-MO-01",
          "priority": "P0",
          "category": "正向主流程",
          "scenario": "查询订单列表-默认加载",
          "precondition": "用户已登录且有页面访问权限，数据库中存在订单数据",
          "steps": [
            {
              "stepNo": 1,
              "action": "导航到「我的订单」页面",
              "expected": "页面正常加载，显示查询表单和订单列表表格"
            },
            {
              "stepNo": 2,
              "action": "观察表格数据",
              "expected": "表格显示订单数据，列头包含：订单编号、订单日期、状态、金额等"
            },
            {
              "stepNo": 3,
              "action": "观察分页组件",
              "expected": "分页组件显示总条数，默认每页 10 条"
            }
          ],
          "testData": "至少 15 条订单数据（超过一页）",
          "relatedDiff": "D1"
        }
      ]
    }
  ]
}
```

### 场景覆盖规则

每个页面必须覆盖以下 5 个维度：

| 维度 | 来源 | 优先级 |
|------|------|--------|
| 正向主流程 | diff 验收点的“正向场景” | P0 |
| 反向校验 | PRD 的业务规则 + 状态流转 + 控件矩阵中的页面级校验 | P1 |
| 边界场景 | diff 验收点的“空态” + 分页边界 + 特殊字符 | P2 |
| 权限控制 | diff 验收点的“权限态” + 9 维度中的“权限与角色” | P1 |
| 异常场景 | diff 验收点的“异常态” + 接口失败 | P2 |

补充约束：

- 只要页面包含新增、编辑、审核、提交、作废、删除、导出、确认、发货、取消发货、批量操作等业务动作，反向校验至少生成 2 条，其中至少 1 条必须是“业务规则反向”或“状态流转反向”。
- 纯必填/格式校验最多 1 条；如果只是组件级通用校验且没有业务差异，可以不单独生成。
- 导出、批量操作、状态变更类页面，优先覆盖“筛选条件不满足”“状态不允许”“数据范围不匹配”“操作后结果未同步”这类偏业务的反向场景。

### Traceability 规则

`relatedDiff` 只允许填写真正被该用例验证的 `Dx/Bx` 编号，多个编号用英文逗号分隔。

严格规则：

- 不要把 `D1`、`D3` 这类编号当成“通用桶”挂到大量无关页面上。
- 如果 diff 编号描述的是某个明确页面，只有该页面的用例可以引用它。
- 如果引用的是“页面标题”“固定列”“供应商证件号字段”“高级搜索缺少字段”“按钮缺失”“弹窗不符”这类差异，用例步骤或预期结果中必须显式出现对应断言，不能只挂编号不验证内容。
- 如果某个 diff 项属于研发待实现问题，而不是 QA 手工可执行场景，不要放进 `relatedDiff`。

### 编号规则

`TC-{页面缩写}-{序号}`

页面缩写取 `pageSlug` 的大写首字母缩写，最多 3 个字母：

- `my-order` -> `MO`
- `delivery-record` -> `DR`
- `consignment-inventory` -> `CI`

序号从 `01` 开始，按最终 JSON 中的顺序连续编号。优先级排序要求 `P0` 在前，再 `P1`，最后 `P2`。

用 `Write` 工具保存 JSON 文件到已确认的输出目录。

需要完整字段示例时，读取 `references/test-case-example.json`。

## Step 4: 校验 JSON 并生成 Excel

先校验，再生成 Excel：

```bash
npm --prefix "<skill目录>/scripts" install
node "<skill目录>/scripts/validate-test-cases.js" "<JSON文件绝对路径>"
node "<skill目录>/scripts/generate-excel.js" "<JSON文件绝对路径>" "<输出目录>/test-cases.xlsx"
```

`validate-test-cases.js` 和 `generate-excel.js` 均位于 `skills/prd-test-cases/scripts/`。

校验脚本负责检查至少以下内容：

- 顶层字段是否完整
- 用例编号是否唯一且连续
- 分类是否属于允许集合
- 每页是否覆盖 5 个场景维度
- 含业务动作的页面是否满足最小反向用例要求
- `relatedDiff` 是否引用了真实存在的 `Dx/Bx`
- 页面级 diff 是否被错误地挂到其他页面
- 是否混入实现缺陷型用例

如果校验失败，先修复 JSON，再继续生成 Excel。

即使 Excel 与 JSON 放在同一目录，也要显式传入 `<输出目录>/test-cases.xlsx`，避免落到未确认的位置。

## Excel 结构

### Sheet 结构

- 每个页面一个 Sheet（sheet 名 = 页面中文名，如“我的订单”）
- 最后一个 Sheet 为“汇总”

### 列定义

| 列 | 列头 | 宽度 | 说明 |
|----|------|------|------|
| A | 用例编号 | 15 | `TC-{缩写}-{序号}` |
| B | 优先级 | 8 | `P0 / P1 / P2` |
| C | 场景分类 | 15 | `正向主流程 / 反向校验 - 业务规则 / 反向校验 - 状态流转 / 反向校验 - 输入校验 / 边界场景 / 权限控制 / 异常场景` |
| D | 场景名称 | 30 | 业务场景描述 |
| E | 前置条件 | 30 | 执行该用例前需要满足的条件 |
| F | 步骤序号 | 8 | `1, 2, 3...` |
| G | 操作步骤 | 40 | 具体操作描述 |
| H | 预期结果 | 40 | 该步骤的预期结果 |
| I | 测试数据 | 25 | 需要的测试数据，可为空 |
| J | 关联差异 | 12 | 对应 diff 的 `Dx/Bx` 编号 |

### 样式规则

- 表头：加粗、蓝色背景(`#4472C4`)、白色字体
- 优先级颜色：`P0=#FFC7CE`，`P1=#FFE699`，`P2=#D9E2F3`
- 同一场景的多步骤：合并 `A-E`、`I-J` 列
- 首行冻结
- 启用筛选

### 汇总 Sheet

| 页面 | P0 数量 | P1 数量 | P2 数量 | 总计 |
|------|--------|--------|--------|------|
| [页面名] | [N] | [N] | [N] | [N] |

## 完成条件

- [ ] 每个 diff 文档中的页面都有对应的测试用例
- [ ] 每个页面覆盖 5 个场景维度（正向 / 反向 / 边界 / 权限 / 异常）
- [ ] 包含业务动作的页面满足最小反向用例要求
- [ ] 不包含实现缺陷型用例
- [ ] `relatedDiff` 只引用真实存在且页面匹配的 `Dx/Bx`
- [ ] 页面级差异（标题 / 固定列 / 缺少字段 / 按钮 / 弹窗等）被显式断言，而不是只挂编号
- [ ] JSON 校验脚本通过
- [ ] Excel 文件已生成且可正常打开
- [ ] 用例编号唯一且连续
