# 后端测试规范（当前若依工程）

## 1. 目标

后端测试不是“补几个断言”就结束，而是要把 RuoYi 后端的接口行为、业务规则、SQL 风险点和回归点明确下来。

本规范用于回答三个问题：

1. 这一层**该测什么**
2. 这一层**不该测什么**
3. 在仓库没有现成测试基建时，什么时候允许先做手工验证与测试文档沉淀

## 2. 分层测试边界

### 2.1 Controller 层

**重点验证：**

- 路由、HTTP 方法、权限字符串是否正确
- 参数绑定、分页入参、导出 / 导入入口是否符合预期
- 列表接口是否返回 `TableDataInfo`
- 新增 / 修改 / 删除 / 明细接口是否返回 `AjaxResult`
- 无权限、非法参数、状态不允许操作时是否返回正确响应

**不要在 Controller 层重复验证：**

- 复杂业务规则的完整分支
- Mapper / SQL 细节
- 与框架无关的纯算法逻辑

### 2.2 Service 层

**重点验证：**

- 核心业务规则
- 状态流转限制
- 重复数据 / 不存在数据 / 禁用状态等关键分支
- 事务边界、异常抛出或错误返回
- 新增 / 修改 / 删除时审计字段、默认值、软删策略是否符合约定

**不要在 Service 层重复验证：**

- Spring MVC 路由细节
- 页面字段显隐、前端展示文案

### 2.3 Mapper / SQL 层

**重点验证：**

- 自定义 SQL 是否正确过滤条件
- 动态 SQL、时间范围、模糊查询、状态过滤是否符合预期
- 分页、排序、软删条件、数据范围条件是否遗漏
- 联表字段映射、返回列别名是否与领域对象一致

**适用场景：**

- 复杂查询
- 手写 XML
- 容易回归的 where 条件组合

## 3. RuoYi 响应断言要求

### 3.1 `AjaxResult`

新增、修改、删除、明细等普通接口至少关注：

- `code`
- `msg`
- `data`（如有）

如果业务约束要求明确错误提示，测试中必须断言错误语义，而不是只断言“失败了”。

### 3.2 `TableDataInfo`

列表接口至少关注：

- `rows`
- `total`
- 分页参数对结果的影响
- 软删 / 权限 / 状态过滤后的可见数据

不要只断言 HTTP 200，而忽略 `rows`、`total` 的结构和数量。

## 4. 必测分支

### P0：主流程

- 列表查询成功
- 明细查询成功
- 新增成功
- 修改成功
- 删除成功（或软删成功）

### P1：关键分支

- 无权限访问
- 目标数据不存在
- 重复主业务字段
- 状态不允许操作
- 关键必填 / 业务前置条件不满足

### P2：边界与异常

- 分页边界、空列表、空结果
- 时间范围、状态字段、特殊字符
- Mapper 查询条件组合
- 后端异常、数据库异常、外部依赖失败

## 5. 什么时候允许先做手工验证

允许先产出测试文档与验证计划、暂不新增自动化测试的场景：

- 当前目标仓库尚未落地后端自动化测试基建
- 本次改动仅为低风险配置 / 文档 / 模板调整
- 本次只是生成器骨架或结构性搬运，尚未引入新的业务规则
- 任务明确要求“先完成详细设计 / test cases / 手工回归路径”，后续再补自动化测试

即便允许手工验证，也必须先产出：

- `docs/plans/YYYY-MM-DD-<topic>-test-cases.md`
- 明确的验证步骤
- 至少一轮主流程 + 关键分支回归计划

## 6. 什么时候应优先补自动化测试

以下情况建议优先补自动化测试，而不是只写手工验证：

- Service 层存在复杂状态机或关键业务分支
- Mapper / XML 查询复杂且容易回归
- 高风险缺陷修复需要防回归
- 权限、软删、数据范围等若依高频坑点被改动

## 7. 用例到自动化测试的映射格式

测试用例文档中，P0 / P1 用例必须能映射到自动化测试方法，推荐格式：

```md
## 自动化测试映射

| 用例编号 | 优先级 | 建议测试层 | 测试文件 | 测试方法 |
| --- | --- | --- | --- | --- |
| TC-ORDER-LIST-001 | P0 | Controller | `OrderControllerTest.java` | `shouldReturnPagedOrderList()` |
| TC-ORDER-STATUS-002 | P1 | Service | `OrderServiceTest.java` | `shouldRejectCancelWhenOrderCompleted()` |
| TC-ORDER-MAPPER-003 | P1 | Mapper | `OrderMapperTest.java` | `shouldFilterDeletedOrdersInListQuery()` |
```

## 8. 常见错误

- 只测 HTTP 200，不测 `AjaxResult` / `TableDataInfo` 结构
- 只写 happy path，不写权限、状态、异常分支
- 在 Controller 测试里塞满业务规则断言，导致职责混乱
- 有复杂 XML 查询却没有任何 Mapper 级验证
- 仓库没有测试基建时，既不补自动化测试，也不落盘 test cases

## 9. 最低结论

后端任务至少要做到：

1. 明确主流程与关键分支
2. 明确分层测试边界
3. 对 `AjaxResult` / `TableDataInfo` 做结构化断言
4. 把 P0 / P1 用例映射到自动化测试文件 / 方法，或明确说明当前为何先只做手工验证
